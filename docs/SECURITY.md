# Безопасность SSH Mobile

Документ описывает модель угроз, реализованные меры и границы защиты MVP v0.1.

## 1. Защищаемые активы

- пароли SSH;
- приватные ключи и passphrase;
- список серверов и их параметры;
- доверенные host key (known hosts);
- содержимое терминальных сессий (вывод команд, секреты в выводе).

## 2. Модель угроз

| Угроза | Мера |
|---|---|
| Кража/извлечение БД приложения | Секреты только в виде AES-256-GCM шифротекста; ключ в Android Keystore |
| Копирование БД на другое устройство | Ключ не экспортируется; расшифровка невозможна, GCM обнаруживает подмену |
| MITM при первом подключении | Показ SHA-256 fingerprint и явное подтверждение; по умолчанию ничего не доверяется |
| MITM при повторном подключении | Сравнение с known_hosts; при смене ключа — предупреждение и повторное подтверждение |
| Утечка секретов в логи | Секреты не логируются; SSHJ использует `slf4j-nop`; сообщения об ошибках не содержат креды |
| Утечка через backup | `allowBackup=false`, data extraction rules исключают БД/файлы/prefs |
| Подмена сервера после reinstal | Fingerprint меняется → предупреждение; пользователь решает осознанно |
| Случайное раскрытие экрана | Опциональный `FLAG_SECURE`; выключен по умолчанию, чтобы не мешать скриншотам |
| Вредоносный сервер, пытающийся записать clipboard | OSC 52 не поддерживается; OSC 8/hyperlinks не открываются автоматически |
| Потеря устройства | Защита ограничена блокировкой ОС; биометрический gate для ключа не реализован |

Вне модели угроз: root/взломанное устройство, вредоносное ПО с accessibility-доступом,
физический доступ к разблокированному устройству, компрометация самого сервера,
слабые пароли пользователя, атаки на цепочку поставок зависимостей.

## 3. Секреты в покое

`AndroidKeystoreSecretCipher`:

- alias `sshmobile.secrets.v1`;
- AES-256, режим GCM/NoPadding, случайный IV на каждое шифрование;
- ключ генерируется в `AndroidKeyStore`, `setRandomizedEncryptionRequired(true)`,
  StrongBox используется при поддержке, иначе TEE;
- формат payload: `v1:<base64url(iv)>:<base64url(ciphertext)>`;
- при повреждении/подмене шифротекста расшифровка падает, репозиторий отдаёт
  `CredentialsUnavailableException`, приложение просит ввести креды заново;
- ключ можно удалить через Settings → Wipe all app data.

В `servers.secret` лежит либо пароль, либо приватный ключ (в зависимости от `authType`);
в `servers.passphrase` — passphrase. Открытый текст не пишется в Room и не показывается
обратно в UI после сохранения.

`keySummary` (тип ключа и fingerprint) хранится открыто: это публичная информация, нужная
для идентификации ключа.

## 4. Host key и MITM

- Используется только `KnownHostsHostKeyVerifier`; `PromiscuousVerifier` и отключение проверки
  в коде отсутствуют.
- Fingerprint — OpenSSH-совместимый `SHA256:` от SSH wire-format public key blob.
- Первое подключение: диалог с fingerprint, host:port, типом ключа; кнопка Accept добавляет
  ключ в known_hosts, Reject прерывает handshake.
- Повторное подключение: ключ того же алгоритма сравнивается constant-time; совпадение
  не требует участия пользователя.
- Смена ключа: отдельный красный диалог «Host key has changed» со старым и новым
  fingerprint и предупреждением о возможном MITM. Accept заменяет запись; Reject
  останавливает подключение и авто-reconnect.
- Разные алгоритмы (RSA/ECDSA/ED25519) хранятся отдельно; сервер может предъявить другой
  алгоритм — это трактуется как новый ключ, а не как изменение известного.
- BouncyCastle устанавливается как JCE provider для корректной работы ключей на Android;
  это не отключает проверку host key и не влияет на политику доверия.

Ограничение: пользователь может подтвердить подменённый ключ, если сравнит fingerprint
небрежно. UI явно просит сверять его с администратором/консолью сервера.

## 5. Ключи и память

- Приватный ключ импортируется через SAF, проверяется `PrivateKeyInspector` (реальный парсинг
  SSHJ) до сохранения; отображаются тип и fingerprint.
- Passphrase передаётся в SSHJ через `PasswordUtils.createOneOff`, который затирает исходный
  char[] после использования.
- Во время сессии расшифрованные креды находятся в памяти процесса и внутри SSHJ; после
  подключения ссылки на них не сохраняются в долгоживущих полях.
- Приватные ключи не копируются в логи, crash-отчёты и файлы приложения.
- Автопереподключение повторно расшифровывает креды из БД; это осознанный trade-off
  (иначе reconnect невозможен без участия пользователя).

## 6. Логи и диагностика

- В приложении нет логирования паролей, ключей, passphrase или полного вывода терминала.
- SSHJ использует SLF4J binding `slf4j-nop`; его debug-логи отключены.
- Сообщения об ошибках показывают класс проблемы (DNS, timeout, auth, host key, key format),
  но не содержимое секретов.
- Debug APK не содержит инструментов логирования секретов; release дополнительно
  минифицирован R8.

## 7. Clipboard, экран, backup

- Вставка идёт из системного clipboard; приложение не читает clipboard автоматически.
- Копирование помещает выбранный текст в общий clipboard Android — другие приложения могут
  его прочитать. Это стандартное поведение; не копируйте секреты без необходимости.
- `FLAG_SECURE` включается настройкой «Block screenshots»; по умолчанию выключен.
- Backup отключён; экспорт конфигураций (v0.2) должен исключать секреты.
- Файлы ключей, импортированные пользователем, остаются в исходном месте (Downloads и т.п.);
  приложение не удаляет их. Пользователю рекомендуется удалить файл после импорта.

## 8. Сессии и жизненный цикл

- Сессии живут в процессе приложения; при убийстве процесса ОС закрывает сокеты и сессии
  пропадают.
- Явное закрытие освобождает transport, shell, coroutines и ожидающие host-key запросы.
- Приложение не использует foreground service в MVP, поэтому не обещает фоновое удержание
  соединения при агрессивном battery management.
- Терминальные escape-последовательности обрабатываются локально; приложение не исполняет
  команды, не открывает ссылки и не отправляет данные по инициативе сервера.

## 9. Что не защищено

- Устройство с root/кастомной прошивкой или активным malware может читать память и ввод.
- Скриншоты/запись экрана возможны, если пользователь не включил FLAG_SECURE.
- Буфер обмена общий для приложений.
- Нет биометрической защиты для конкретного сервера.
- Нет защиты от вредоносного сервера, которому пользователь сам выдал доступ.
- Нет SSH agent/FIDO: приватный ключ должен находиться в приложении.
- Нет certificate pinning для сторонних HTTPS-запросов (их в MVP нет).

## 10. Рекомендации пользователю

1. Сверяйте fingerprint при первом подключении с доверенным источником.
2. Не подтверждайте изменившийся host key без выяснения причины.
3. Используйте отдельные ключи для мобильного клиента и passphrase на ключах.
4. Включите Block screenshots, если в терминале бывают секреты.
5. Удаляйте импортированные файлы ключей после добавления в приложение.
6. Для утери устройства используйте удалённую блокировку/стирание ОС; приложение не хранит
   экспортируемый мастер-ключ.

## 11. Сообщение об уязвимости

Не публикуйте детали уязвимости в открытом виде до исправления. Приложите версию APK,
модель/версию Android, шаги воспроизведения и не прикладывайте реальные пароли/ключи.
